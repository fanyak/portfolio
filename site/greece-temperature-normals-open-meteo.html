Recreating a Data-Driven Temperature Normal for Greece

Fani Akritidou • 20 min read • Data Analysis

Building a national temperature anomaly chart in Python, with public sector and Open-Meteo data, using cross-validated smoothing.

Note: This post was inspired by Dominic Royé's article: Royé, Dominic. 2026. “A Data-Driven Normal for the Spain Temperature Chart.” June 23.
It is a great article and you should go read it! Here I recreate the methodology in Python, using data from the recently redesigned National Data Portal.

Setting the Goal

Comparing daily temperature data provides little information about how mean temperatures actually differ between years. What is more informative is a smooth daily climatological reference, which allows us to compare data without the day-to-day noise. Creating a climatological normal, a normal year curve, against which we can plot a year's values is the theme of Dominic Royé's article.

The challenge is to figure out how to create such a smooth curve out of noisy data, without either following the noise or flattening real features. This is a model-selection problem where we must choose between families of smoothers. The preferred families for this project are two: loess(locally weighted regression) and harmonic regression. Both of these smoothers can be tuned and (re-)evaluated in a cross-validation process.

The end goal is to recreate Dominic Royé's chart for the daily mean temperature against its climatological normal, only instead of data for Spain I am using data for Greece and instead of R I am using Python.

Note: the original article used historical data for the years 1961-1990, downloaded from Open-Meteo, as the reference set. This project is (partly) an exercise in using data from Greece's newly renovated National Portal, where the historical data that is available starts in 2010 and ends in 2023. I used this set as the reference and downloaded the data for 2025 from Open-Meteo (as was done in the original article).

Tools

To port the original methodology from R to Python I used the following packages:

Smooth the Curve

Next step is to select the best smoothing function. This is a model selection task: pick the member of a family of smoothers that best predicts unseen data, using cross-validation.

As in the original article, the 2 smoothers that I evaluated are Harmonic Regression and Locally weighted regression

Harmonic Regression

As Dominic Royé explains:

Harmonic Regression models the climatological curve as a sum of sine/cosine pairs with a 366-day period.

The sum of the sine/cosine pairs are linear predictors, as in OLS. An instance of this model takes two parameters:

  • K, which represents the harmonic order (e.g., 1 for 1st harmonic, 2 for 2nd, etc).
    The higher K is, the less smoothing we get, and the higher the variance of the model.
  • period, the period of the cycle. In our case, period is fixed at 366 days to account for leap years.

While period is fixed, parameter k is a hyperparameter that we need to tune in order to get the model that best predicts the 2025 data.

Again, from the original article:

To find the best K we fit on the daily data directly (not an already-aggregated climatology), using k-fold cross-validation split by year, so a given year's 365/366 days stay together, fully in training or fully in test.

For each chosen value of K we repeat the following process n_split times:

  1. create a new OLS model for the selected K order,
  2. hold out the days of the current iteration's test fold years,
  3. fit the model on the days of the training folds' years,
  4. use the fitted model to predict the held-out days,
  5. estimate the model's error of the nth iteration using the RMSE loss function.

Finally, the estimated performances (RMSE) of all the n_split iterations are used to calculate the estimated average (mean) performance for each K.

Locally weighted regression

Loess (lowess) works locally, meaning that to make an estimate of a value it uses a fraction of the data that is near-by that value. The size of the fraction is a hyperparameter of the model.

Specifically, in the statsmodels package( statsmodels.api.nonparametric.lowess ) this parameter is named frac:

Suppose the input data has N points. The algorithm works by estimating the smooth y_i by taking the frac*N closest points to (x_i,y_i) based on their x values and estimating y_i using a weighted linear regression. The weight for (x_j,y_j) is tricube function applied to abs(x_i-x_j).

The loess regression runs on data structured as climatology, meaning that instead of the raw daily points for years 2012-2023 it needs one summarized value per day over all the years. This however creates a problem: since the model uses the frac*N closest points we have to make day 366 and day 1 be adjacent, since they are calendar adjacent. As in the original article, to adress this I glued three copies of the climatology end to end, smoothed the concatenated data, and kept only the middle copy.

Code

Note: the statsmodels lowess implementation takes a second (hyper)parameter it. If it > 1, then further weighted local linear regressions are performed. This is most useful when the noise has "extremely heavy tails" (Cauchy noise). Since our climatology noise is closer to a t-distribution than to Cauchy, I kept the default it = 1.

The frac parameter controls roughly how much of the data is used locally for each fitted point.

  • frac=0.01 → follows the data closely, potentially noisy
  • frac=0.1 → moderate smoothing
  • frac=0.3 → very smooth, potentially hiding real structure

It is easy to see that the best value is close to 0.05. Again, cross-validation will tell us what the best value is.
I followed the same process as in the harmonic regression, except of course now the aim is to find the best value for the frac hyperparameter.
